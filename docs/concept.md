# s3d のコンセプト（ダーリン定義、2026-10-31）

これは「あるべき」の定義。ダーリン本人がこの窓で述べたものが正で、コードの現状（code-spec.md）とは分けて扱う。

## 責務

s3d は **simple-static-site-deployer**。

静的ウェブサイト作成の際、HTML 実装のときの重いファイルを、

- デプロイ時に軽量化したり、
- 仮画像で置いたり、
- 非同期に CDN で配信物を取得したり、
- 重いものを優先的にキャッシュしたり

することで、ウェブサイトの可用性を上げる道具。

## 強みは3つ（3担当に責任を分ける）

| # | 強み | 誰のため | 内容 |
|---|---|---|---|
| 1 | Deploy の単純さ | インフラエンジニア | デプロイが単純で楽になる |
| 2 | Display の明快さ | フロントエンジニア | 確認・検証が単純になる |
| 3 | Draft 概念 | モデラー・デザイナー（フロントやバックを知らない人） | ローカル完結で画像・動画・3Dモデルなどの重量級素材を静的サイトに配置でき、フロントエンジニアへ実装連携できる |

名前の読み（セリナの解釈、ダーリン未確認）: s3 = Simple / Static / Site の3つの S、3d = Deploy / Display / Draft の3つの D。「s3 であり 3d である」ことが強み、というダーリンの言い方に対応する。

## 設計原則

- 責任を3担当に分ける。
- それぞれに標準機能が付いているので、どれか1つだけでも強みがあれば使える（単体で採用できる）。

## 周辺の構想

- promote / admit は、メールや色んなものを通じて P2P で行えるようにする。開発から運用まで、サーバのいらない開発体制を組めるようにするため。
- アドオンを追加してバックエンド機能等を追加できるようにし、API 経路をハンドリングできるようにして、開発中の混線を極力なくしていく。

## Draft のプレビューURLと近距離ホスティング（2026-10-31 ダーリンの追加）

ダーリンの言い方: 「プレビューURL概念が使えるほうがいい」「近距離ホスティングとかできたらいいのに」。

セリナの整理（提案、未確定）:

- Draft をネイティブアプリ化する場合も、プレビューURLの概念は残す。置いた素材をその場でURLとして見せられることが、営業デモやフロント連携の強みになる。
- 近距離ホスティング: Draft アプリ自身が一時的なローカルHTTPサーバになり、同じLAN内のスマホ等へプレビューURL（QRコード、mDNS の .local 名など）を出す。重いGLBや動画をクラウドへ上げる前に、手元の端末から直接配信して確認できる。
- 遠距離共有は従来どおり R2 / Pages 等の仮デプロイURLが担い、近距離はローカル配信が担う、という二層にすると「サーバ不要」「ローカル完結」「URLで見せられる」を両立しやすい。
- 安全側の最低限: 明示的に開始/停止する、読み取り専用、URLに一時トークンを付ける、期限を切る、LAN外へは出さない。動画や3Dで効くので Range リクエスト対応も前提にする。

## Draft 仕様協議（統合版、2026-10-31 ダーリン指示で一本化）

経緯: Draft 系を細分化した issue #46（ネイティブアプリ設計）・#47（近距離ホスティング）・#48（promote/admit P2P）は、ダーリンの指示「ドラフトは全部閉じて1概念にまとめろ。ドラフト仕様協議でいい」で閉じ、協議は統合 issue 1件に寄せる。詳細の下書きは issue-drafts-2026-10-31.md に残置（md でまとめておく、という同日の指示）。

統合した Draft の概念:

1. 担い手: フロント/バックを知らないモデラー・デザイナー。重量級素材（画像・動画・3Dモデル）を静的サイトへローカル完結で配置し、フロントエンジニアへ実装連携する。
2. 置き方: 本番を再現した空間/ページへ素材を置き、位置・スケール・回転・カメラ・クリック時挙動を調整して、設定差分（config 差分相当）として書き出す。
3. 見せ方: プレビューURLの概念を必ず使えるようにする。近距離は Draft 自身のローカル配信（LAN・QR・トークン・期限・Range）、遠距離は R2 / Pages の仮デプロイURL。
4. 渡し方: promote / admit はメール等の媒体で P2P に行えるようにし、サーバ不要の開発〜運用体制を組む。環境は draft / staging / production。
5. 段階（ダーリンの見立て、2026-10-31）: まず deploy と display で「アプリの簡単なもの」は作れる。ネイティブ GUI はその先の本命として協議を続ける。

## 現状との対応（2026-10-31 時点、セリナの対応付け）

| 強み | 現状 |
|---|---|
| Deploy | build / push / diff / validate はある。ただし「デプロイ時に軽量化」が無い（static3d の GLB 最適化に相当するものが s3d には無い） |
| Display | 仮画像（initial）＋自動差し替えは Issue #41 で実装済み。確認・検証のための serve / preview は無い |
| Draft | 一番薄い。strategy の宣言はあるが、draft の置き場・配置ワークフロー・promote / admit が無い（static3d には R2 プレフィックス版の環境＋promote/admit があった。P2P 版はどちらにも無い新規構想） |
| アドオン / API | 未実装。既存 open issue #18（プラグイン）と #29（DB戦略）がこの方向の先行議論 |
